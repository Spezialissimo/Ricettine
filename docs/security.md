# Security

What the code and infrastructure do today, with where to find it. This is a small self-hosted app, not an audited product: the list is the set of measures, not a guarantee.

## Accounts

- **Invite-only.** The first visitor of a fresh install creates the admin (`/api/setup/admin`, open only while no user exists). After that, accounts are created through single-use invite links made by an admin. Invite links expire after 7 days (`InviteService`).
- **Passwords** are hashed with Argon2 (Spring Security's current defaults, about 16 MB per hash). Old bcrypt hashes still verify.
- **Bounded hashing.** Argon2 is memory-hungry and login is unauthenticated, so at most 4 hashes run at once (`RICETTINE_SECURITY_MAX_CONCURRENT_HASHES`). A request that waits more than 10 seconds gets 503 `busy` instead of exhausting the heap (`BoundedPasswordEncoder`).
- **No account probing.** Login for an unknown email still verifies against a dummy hash, and the same limits apply to known and unknown emails.
- **Tokens** (invites, password resets, cookbook invites) are random and only their SHA-256 hash is stored. Recipe and cookbook share links use random tokens too, and can be reset.

## Sessions and CSRF

- Sessions are stored in Postgres (Spring Session JDBC). The `SESSION` cookie is HttpOnly and SameSite=Lax, valid for 30 days. `Secure` follows the request scheme, which is correct behind a TLS proxy only when that proxy is trusted (see below).
- CSRF uses Spring Security's SPA mode: an `XSRF-TOKEN` cookie that Angular reads and sends back as `X-XSRF-TOKEN` on writes.
- Responses carry a Content-Security-Policy (`default-src 'self'`, `object-src 'none'`, `frame-ancestors 'none'`) and `Referrer-Policy: same-origin`. A Playwright spec (`csp.spec.ts`) covers it.
- The media route has its own filter chain without CSRF handling, so an image response never sets an `XSRF-TOKEN` cookie that a shared cache could hand to other viewers.

## Rate limits

In-memory, per instance, counted in fixed windows (`ricettine.limits.*` in `application.yml`). A rejected request gets 429 `too_many_attempts` with `Retry-After`. The checks run before any password hash or image decode.

| Limit | Default |
| --- | --- |
| Login per account (normalised email) | 10 per 15 min |
| Login per IP | 30 per 15 min |
| Sign-up and setup per IP | 30 per 15 min |
| Demo guest sign-in per IP | 30 per 10 min |
| Uploads per user | 60 per 10 min |
| Profile page reads, per user (per IP on the demo) | 120 per minute |

Only failed logins count against the account; a correct password clears it. IPv6 clients are keyed by their /64.

## Origin secret and trusted proxies

- **Origin secret.** On AWS the origin port 443 is open only to the CloudFront prefix list, which other accounts share. CloudFront therefore adds `X-Origin-Verify` with a random secret, and Caddy answers 403 without it, then removes it before the app. The secret and the database password are generated by Terraform and read from SSM Parameter Store at boot (`deploy/aws/start.sh`); the instance role can read only `/ricettine/*` parameters.
- **Trusted proxies.** The app believes `X-Forwarded-For` only from peers matching `RICETTINE_TRUSTED_PROXIES`; the default matches nothing, so a direct `docker run -p 8080` cannot spoof its address. The Caddy overlays trust their own Docker network. The RFC 7239 `Forwarded` header is ignored and also removed by Caddy.
- **Site header.** `X-Ricettine-Site` selects the demo database and is trusted blindly, so only the edge may set it (see demo isolation below).

## Crawlers

Every response, including 401 and 403, carries `X-Robots-Tag: noindex, nofollow` (`RobotsHeaderFilter`, checked by `noindex.spec.ts`). There is no `robots.txt` Disallow on purpose: a crawler that is not allowed to fetch a page never sees the noindex.

## Media access

Images are served by `/media/{id}/{variant}.jpg`. A per-kind access policy decides each request; a denied request gets 404, so existence is not revealed.

- **Avatars** are readable by everyone and cached as immutable.
- **Recipe photos** are readable by the owner, or by someone with the recipe's share token (`?s=`) while the recipe is published.
- **Cookbook covers** are readable by the owner and co-authors, or with the cookbook's share token (`?c=`).
- Share-link and cover responses use `no-cache`, so a reset link or a removed co-author takes effect at once.
- Uploads are limited to 15 MB, decoded and re-encoded to JPEG variants (nothing the client sends is stored as is), and at most 2 images decode at once.
- Adding a photo from a web address refuses any address on a private, loopback, link-local (including the cloud metadata address) or otherwise non-public range, after resolving the name (`PublicAddresses`, `RemoteImageFetcher`).
- The S3 buckets block all public access, are encrypted, and deny non-TLS requests. The instance role can read, write and delete media objects, but only put (not delete) database dumps.

## Demo isolation and read-only behaviour

- The demo is a separate database (`ricettine_demo`) behind a routing `DataSource`; queries of one site cannot reach the other. Its blobs use a separate `demo/` key prefix and are wiped at each start.
- The site is chosen only by the `X-Ricettine-Site` header. The demo CloudFront distribution sets it as an origin header (which overrides any viewer value); the main distribution never forwards it from viewers; the self-host Caddyfiles set it on every request.
- `DemoReadOnlyFilter` refuses any method other than GET, HEAD and OPTIONS on the demo with 403 `demo_read_only`. It runs before the session and security layers, so a refused request creates no session. The exceptions, matched on the exact path, are `POST /api/demo/session` and `POST /api/auth/logout`.
- Guest sign-in is `ospite`, a user with a random, discarded password that nobody can log in with, limited to 30 sign-ins per IP per 10 minutes, with a one-day session. The demo's seeded addresses end in `@demo.invalid`.
- The demo has no admin and no setup form.

## Logs

Request URIs contain secrets (invite, reset and share tokens are in paths), so they are kept out of logs.

- The AWS Caddyfile has no access log. Caddy's error log has request URIs and headers removed (`request>uri delete`, `request>headers delete`), which also covers cookies.
- The app configures no access log, and the self-hosting `deploy/Caddyfile` has no access log either.

## Backups

- A systemd timer runs `deploy/backup.sh` daily at 03:00 UTC: `pg_dump` of the `ricettine` database, uploaded to a separate S3 bucket. The demo database is disposable and not dumped.
- The instance may only put objects under `db/`; versioning is on and old dumps expire after 30 days (the default `backup_retention_days`).
- A CloudWatch alarm fires when no dump arrives for 26 hours, and a failed run sends an alert.
- Photos in the media bucket are versioned, so a deleted photo stays recoverable for the same period.
- `scripts/backup-restore-check.sh` backs up, wipes and restores a stack, and runs in CI.
- Data and root volumes are encrypted; the data volume has `prevent_destroy`.

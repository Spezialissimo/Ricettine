# Decisions

The main design decisions, in short ADR form. Each one is what the repository does today; the consequences include the costs.

## 1. Single image instead of services

**Context.** The app is for friends and family and is self-hosted by people who want `docker compose up` and nothing else.
**Decision.** One Spring Boot application serves the API and the built Angular files. One Docker image, plus Postgres in `compose.yaml`. No required configuration: the first visitor creates the admin.
**Consequences.** Deploying and upgrading is one image pull, and the frontend and backend cannot drift apart. The cost is that they scale and release together, which does not matter at this size. Migrations run on startup.

## 2. Server-assigned ids and a client-agnostic API

**Context.** A native Android client may come later and must not need web-specific behaviour.
**Decision.** The API is plain JSON with problem+json errors. Ids are generated by the server, never by the client. Recipes carry a `version` for optimistic locking.
**Consequences.** Any client can use the API, and clients cannot choose or guess ids. A client has to create a draft first and then save it, one round trip more than client-generated ids would need.

## 3. No PWA, a native app later

**Context.** Offline sync and service workers add a lot of machinery that a later native client would replace anyway.
**Decision.** No offline mode, no service worker, no install prompt. The web app is online-only and responsive.
**Consequences.** Less code and fewer cache bugs. The app does not work without a connection. The one exception is small: unsent editor changes are backed up in the browser's local storage (`UnsavedBackup`).

## 4. Desktop first, responsive at 768 px

**Context.** Writing a recipe is easier at a desk; reading it in the kitchen happens on a phone.
**Decision.** Layouts are designed for desktop and adapt at a 768 px breakpoint. Touch targets are at least 44 px. Every browser test runs in a `mobile` and a `desktop` project.
**Consequences.** Both layouts are covered in CI. Visual polish is deliberately deferred: the UI is functional and accessible first.

## 5. One EC2 instance with Compose instead of ECS and RDS

**Context.** A small app with a handful of users. Managed services would cost more than the instance.
**Decision.** One `t4g.small` instance runs Caddy, the app and Postgres with Docker Compose. Data is on a separate EBS volume with `prevent_destroy`. Daily `pg_dump` goes to S3. `scripts/infra-check.sh` fails the build if Terraform declares an RDS, load balancer, ECS, NAT gateway or VPC endpoint.
**Consequences.** Low cost and one place to look. The cost is a single point of failure: a host or database failure means downtime until restore. Restores are practised by `scripts/backup-restore-check.sh` in CI.

## 6. CloudFront in front of the origin, with a secret header

**Context.** The origin allows port 443 from the CloudFront IP list, which is shared with other AWS accounts, so the list alone does not prove a request came from this distribution.
**Decision.** CloudFront adds an `X-Origin-Verify` header with a random secret (kept in SSM). Caddy answers 403 without it and removes it before the app. The client IP reaches Caddy as `CloudFront-Viewer-Address`.
**Consequences.** Direct requests to the origin get 403. The edge also caches `/media/*`. The secret must be alphanumeric because Caddy matches it literally, and rotating it means redeploying both sides.

## 7. Demo isolation by routed database

**Context.** A public demo needs real data and a write-protected state, and must never touch the real recipes. Options: a second instance, one database with a site column in every query, or one instance with two databases.
**Decision.** One instance, two databases (`ricettine`, `ricettine_demo`) on the same Postgres. A request's site comes from the `X-Ricettine-Site` header and a routing `DataSource` picks the pool. The demo database is dropped, recreated, migrated and seeded at every start.
**Consequences.** No query can mix the two sites, and no feature needs a site filter. A second instance would double the memory; query filtering would depend on every query being right. The costs: both sites share one JVM and its memory budget, the header must be set only by the edge, and demo sessions are lost at every restart.

## 8. Read-only demo instead of sandbox accounts

**Context.** Visitors should look around at once, without signing up, and the demo must not become a place where strangers post content.
**Decision.** Visitors are signed in automatically as the guest `ospite`. Any method other than GET, HEAD or OPTIONS is refused with 403 `demo_read_only`, except guest sign-in and logout. The filter runs before the session and security layers.
**Consequences.** Nothing to moderate or clean up, and no per-visitor state. Visitors cannot try the editor with a real save. All visitors share one account, so some rate limits are per client address on the demo.

## 9. Demo content licensing

**Context.** The demo needs recipes and photos that can be shown publicly without breaking anyone's rights.
**Decision.** Recipe text comes from the TheMealDB API and from Wikibooks (CC BY-SA), translated into Italian and adapted. Dish photos are from Unsplash and Pexels. Step-by-step photos are from Wikimedia Commons (CC0, public domain, CC BY, CC BY-SA, Free Art License). Sources and licences are in [CREDITS.md](../CREDITS.md).
**Rejected.** Scraping recipe sites such as GialloZafferano (their text and photos are not licensed for reuse) and using TheMealDB's own images (their licence is unclear).
**Consequences.** Attribution has to be kept and the share-alike licences apply to those texts and images only. Choosing and checking the material took more work than copying would have.

## 10. Sessions in Postgres

**Context.** Logins should survive an app restart, and the stack should stay at two services.
**Decision.** Spring Session JDBC stores sessions in Postgres (30 days, HttpOnly, SameSite=Lax cookie). No Redis.
**Consequences.** No extra service, and signed-in users stay signed in across upgrades. Every request reads the session row. A payload that cannot be read after an upgrade is treated as logged out instead of an error. The demo's guest sessions live in the demo database, so they end when it is recreated.
